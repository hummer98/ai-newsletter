ADR 001 — Discord チャンネル配信の技術設計

Status: accepted  ·  Plan ref: plan:001 (docs/plans/001-discord-delivery.html)  ·  Owns: this file only. 実装は T3 が別タスク。

Context

確定前提（変更不可、plan:001 由来）: Bot Token 認証 / REST v10 POST https://discord.com/api/v10/channels/{channelId}/messages / ヘッダ Authorization: Bot <token> / body {content} / env DISCORD_BOT_TOKEN / channel は Firestore themes/{id}.discordChannelId → output/themes.json 伝搬 / 本文は newsletter-{id}.txt 全文 / メール（Resend）併用 / 1 メッセージ 2000 字上限 → 行境界優先分割。

既存パターン（踏襲対象）: src/application/email-sender.ts = クラス + constructor DI + 集約結果型（SendResult）+ 純粋 splitIntoBatches + delay() + ローカル定数 MAX_RETRIES / 429 リトライ。 本 ADR が決めるのは plan:001 の 5 論点（IF / 分割境界 / 429 / 罫線正規化 / 型伝搬）のみ。

分離の決定

  • 純粋関数 splitIntoMessages(text, limit?): I/O なし・テスト容易（AC2）。 post() から呼ぶ。
  • I/O メソッド post(channelId, text): split → chunk 毎に fetch 逐次送信・429 リトライ・結果集約（AC3）。 fetch はグローバル（Node 20+）。新規依存なし。
  • オーケストレーション scripts/post-to-discord.ts: themes.json 走査・skip 判定・exit code（AC4）。 DiscordSender は src/application/index.ts から re-export。

Decision 1 — DiscordSender インターフェース

ファイル: src/application/discord-sender.ts。constructor で token を受け、env 読みは script 側（テスト容易）。

// src/types/index.ts に追加
export const DISCORD_MESSAGE_LIMIT = 2000;        // Discord 上限（参照用）
export const DISCORD_SAFE_LIMIT = 1900;           // 実分割の既定上限（マージン100）
export const DISCORD_CHUNK_DELAY_MS = 750;        // chunk 間の軽い遅延
export const DISCORD_MAX_RETRIES = 5;             // 429 リトライ上限/chunk

export interface DiscordChunkResult {
  index: number;          // 0-based chunk index
  ok: boolean;
  status?: number;        // HTTP status（取得できた場合）
  error?: string;
}

export interface DiscordPostResult {
  channelId: string;
  totalChunks: number;
  successCount: number;
  failedChunks: number[]; // 失敗 chunk の index 群
  errors: string[];       // 人間/ログ向けメッセージ集約
}

// src/application/discord-sender.ts
export class DiscordSender {
  constructor(token: string);  // 空/空白 token は throw（EmailSender 踏襲）

  // 純粋関数（static でも free function でも可。export 必須＝AC2 テスト対象）
  splitIntoMessages(text: string, limit?: number): string[];

  // I/O: split→逐次POST→集約。例外を投げず DiscordPostResult を返す。
  post(channelId: string, text: string): Promise<DiscordPostResult>;
}
戻り値方針: post() は throw しない（Resend 版 send() と同様、結果型に畳む）。 script 側が DiscordPostResult を集計して exit code を決める。 splitIntoMessages は export された純粋関数として AC2 のユニットテストから直接呼べること。

Decision 2 — 2000字分割アルゴリズム（契約）

実装はこの境界条件に従う。reviewer/inspector はこの一覧で検証する。 既定 limit = DISCORD_SAFE_LIMIT (1900)。"文字数" は JS String.length（UTF-16 単位）で数える — 本文は CJK 中心で BMP のため code point と一致し、1900 マージンが 2000(Discord は code point カウント)を確実に下回る。

  1. 空入力: text === '' → []（空配列）。post() 側は空配列なら送信 0 件・success 扱い。
  2. 行分割の基準: text.split('\n') で行へ分解。各行に '\n' を再付与して結合する（区切りを保存）。
  3. 貪欲結合: 現在バッファに「行 + 改行」を足すと limit を超えるなら、バッファを 1 chunk として flush し、新バッファを当該行で開始。
  4. 単一行が limit 超: 1 行だけで limit を超える場合は limit 単位で強制スライス（slice(0,limit) を繰り返す）。改行境界を待たない。
  5. 末尾改行: 入力末尾の '\n' は出力で温存してよいが、それだけの空 chunk は作らない。各 chunk は trim せず原文を保つ（本文の体裁を壊さない）。
  6. 各 chunk は 1 ≤ length ≤ limit: 空 chunk を出力しない。
  7. 復元可能性: chunks.join('') が概ね原文に一致（境界での改行重複や欠落を生まない）。テストで join('') === text もしくは末尾改行差のみ、を確認。
  8. limit 引数: 呼び出しで limit 指定時はそれを優先（テストで小さい値を渡せる）。未指定で 1900。
flowchart TD
  S([text]) --> E{text == ''?}

Decision 3 — 429 / エラーハンドリング

sequenceDiagram
  participant P as post()
  participant D as Discord REST
  loop chunk 毎（逐次）
    P->>D: POST /channels/{id}/messages {content}
    alt 2xx
      D-->>P: 200/201
      Note over P: successCount++ / 次 chunk 前に delay 750ms
    else 429 Too Many Requests
      D-->>P: 429 { retry_after }
      Note over P: retry_after 秒 待機
retries<5 なら同 chunk 再送
    else 4xx/5xx 非429
      D-->>P: 401/403/404/5xx
      Note over P: failedChunks に index 追加
当該 chunk は中断、以降は継続
    end
  end
  P-->>P: DiscordPostResult 集約（throw しない）
  • 429: 応答 JSON の retry_after（秒、小数あり）を尊重し delay(retry_after * 1000 + 余裕) 後に同一 chunkを再送。 retry_after 欠落時は 1s * (retry+1) のフォールバック。 上限 DISCORD_MAX_RETRIES = 5。超過したら当該 chunk を失敗計上し次へ。 Retry-After ヘッダもフォールバックとして見てよい。
  • chunk 間遅延: 成功 chunk の後、次 chunk 前に DISCORD_CHUNK_DELAY_MS (750ms)。 429 を事前に減らす（per-channel 5 msg/5s 級の制限に対する保険）。最後の chunk 後は不要。
  • 非リトライ（401/403/404/その他 4xx, 5xx）: リトライしない。 failedChunks に index、errors に status + 本文要約を積む。 残り chunk は続行（部分配信を許容、途中で全停止しない）。 401/403 は token/権限の運用問題、404 は channelId 誤り — script ログで識別可能にする。
  • ネットワーク例外（fetch reject）: 非リトライ扱いで chunk 失敗計上・続行。
  • throw しない: post() は常に DiscordPostResult を返す。throw は constructor の token 欠落のみ。

Decision 4 — txt の "====" 罫線等の正規化

結論: 正規化しない（原文 .txt をそのまま投稿）。

  • Discord markdown の見出しは行頭 # /## /###  のみ。 ================== や 【…】 は装飾化されない。setext 見出し（=== 下線）は Discord 非対応。
  • 本文に markdown 制御文字（* _ ~ ` > や裸 URL）が出るが、 現状サンプル（output/newsletter-kSmyXNiKZDznRMGx4G9c.txt）では実害ある誤装飾は見られない。 URL は Discord が自動リンク化するのみで体裁は保たれる。
  • 正規化を入れると「.txt = 配信本文の単一ソース」という不変条件が崩れ、メール本文と乖離する。 投機的抽象化を避ける（plan の minimal 方針）。
  • 将来フック: 万一誤装飾が出たら post() 前段に純粋な sanitize(text) を足せる位置を空けておく（今は実装しない）。

Decision 5 — discordChannelId 型伝搬（fetch-themes）

ファイル: scripts/fetch-themes.ts（+ 参照型は src/types/index.ts）。 文字列のときのみ含める＝後方互換（未設定テーマで key 省略 → AC1）。

interface ThemeData   { /* ... */ discordChannelId?: string; }
interface ThemeOutput { id; title; prompt; discordChannelId?: string; }

// 読み取り（doc.data() から）。文字列のときだけ採用:

  typeof data.discordChannelId === 'string' && data.discordChannelId.length > 0
    ? data.discordChannelId : undefined;

// allThemes.push({ ..., discordChannelId });

// outputThemes.map: undefined のときは key 自体を出さない（...spread で条件付与）
return {
  id: theme.id, title: theme.title, prompt: processedPrompt,

JSON 出力で discordChannelId key が省略されること（: null/: undefined でなく不在）。 post-to-discord.ts 側は typeof theme.discordChannelId === 'string' で投稿対象判定。

post-to-discord.ts の契約（AC4・参考、所有は T3）

  • themes.json を走査。discordChannelId 文字列を持つテーマ = 投稿対象、無いテーマ = skip + ログ。
  • 対象テーマあり && DISCORD_BOT_TOKEN 未設定 → exit 1。 対象テーマ無し → exit 0（token 不問）。
  • 各対象: output/newsletter-{id}.txt 読み込み → sender.post(channelId, text)。 txt 不在は skip + ログ。DiscordPostResult を集計し全体ログ出力。
  • exit code 方針（提案・lead 確認用 open question 参照）: 全 chunk 成功 = 0。 部分/全失敗があっても workflow 側は continue-on-error: true なので script は失敗を非ゼロで返してログ可視化（メール配信は別ステップで阻害されない）。
  • npm script post-to-discord → npx tsx scripts/post-to-discord.ts（CI ビルド後は node dist/scripts/post-to-discord.js）。

Consequences

  • 容易に: 純粋 split の網羅テスト（境界 1〜8）/ fetch モックで 429・4xx 分岐テスト（AC2/AC3）。新規 npm 依存ゼロ（global fetch）。
  • 容易に: テーマ追加で channelId を Firestore に入れるだけ。コード変更不要。
  • トレードオフ（許容）: 逐次送信 + 750ms 遅延でテーマあたり数 chunk なら数秒。並列化しない（rate limit/順序保証優先）。
  • トレードオフ（許容）: 正規化しないため極端な markdown を含む将来本文で誤装飾の可能性 → sanitize フック位置を明示で緩和。
  • 残課題: per-channel rate limit の正確値は未保証。750ms + 429 尊重で実用上吸収。

Alternatives considered

  • discord.js 採用 — 却下。本用途は単発 REST POST のみ。global fetch で十分、依存とコールドスタートを増やさない（minimal 方針）。
  • Webhook URL 認証 — 却下（plan 確定済）。チャンネル数だけ Secret 増、動的テーマ非対応。
  • 1 行超を改行境界まで送る — 却下。超長単一行で無限に詰まる。強制スライスで停止性を保証。
  • 失敗 chunk で全停止 — 却下。部分配信の方が情報損失が小さい。429 のみ再送、他は計上して続行。
  • 投稿時に "====" 罫線を除去/置換 — 却下。.txt 単一ソース不変条件を維持（Decision 4）。
