Design Review 001 — Discord チャンネル配信

Reviewer: design-reviewer（独立コンテキスト） ·  Plan: docs/plans/001-discord-delivery.html (AC1–AC7)  ·  ADR: docs/adr/001-discord-delivery.html  ·  判定: 条件付き GO（Must-fix を T3/T4 着手前に反映）

前提として扱う lead 裁定: (a) 部分失敗時 post-to-discord は exit 非ゼロ・workflow は continue-on-error、(b) チャンク連番プレフィックスは付けない。この2点は再議しない。

総評

全体設計は既存 EmailSender パターン（クラス + 結果型 + 純粋分割関数 + 429 リトライ + delay()）を正しく踏襲しており、構成・分離・所有マップは健全。新規依存ゼロ・global fetch の判断も妥当。ただし分割アルゴリズムの契約に検証不能・自己矛盾する箇所と、workflow 条件式の不整合、2件の AC の検証可能性の穴があり、これらは実装前に潰す必要がある。

Must-fix（実装着手前に解消）

M1 [blocker] 分割アルゴリズムの規約が自己矛盾しており、テスト不能

ADR Decision 2 は次を同時に要求しているが、これらは両立しない:

  • 項7「chunks.join('') === text（または末尾改行差のみ）」
  • 項2「各行に '\n' を再付与して結合」
  • 項5「末尾改行は温存してよいが、それだけの空 chunk は作らない」「各 chunk は trim せず原文を保つ」
  • 項6「空 chunk を出力しない / 各 chunk は 1 ≤ length ≤ limit」

問題点を具体例で示す:

  1. 末尾改行なし入力で join が壊れる。 text = "a\nb" を split('\n') すると ["a","b"]。各行に '\n' を再付与すると "a\n" + "b\n" = "a\nb\n" となり、join('') === text が成立しない（末尾に余分な \n）。「再付与」を最終行はしない、という例外が規約に書かれていない。サンプル output/newsletter-*.txt は末尾改行なし（最終行「このニュースレターは…」で EOF）なので、この差分は実データで必ず発生する。
  2. 連続改行（空行）の扱いが未定義。 サンプル本文は段落間が \n\n で区切られている。"a\n\nb".split('\n') = ["a","","b"]。空行 "" に '\n' を再付与すると "\n"（length 1）。これは「空 chunk 禁止」には抵触しないが、貪欲結合のバッファ内に積まれる前提なのか、それとも単独で flush され得るのかが規約から読めない。境界（空行がちょうど limit 直後に来る）でバッファ flush されると \n 単独 chunk が生じ、項6/項7と衝突しうる。
  3. 「1 ≤ length ≤ limit」と「強制スライス」の境界。 単一行が limit ちょうど（=limit）の場合、項3「足すと limit を超えるなら flush」では超えないので 1 chunk に収まるが、再付与した '\n' を含めると limit+1 になる。limit ちょうどの行 / limit+1 の行 / limit ちょうどのバッファ、の3境界でオフバイワンが起きやすい。規約は「行 + 改行 で判定」と書くが、強制スライス（項4）は slice(0,limit) で改行を含めず limit 単位、と非対称。チャンク実長が limit を超えないことを、改行付与込みで保証する明示が必要。

提案する確定規約（差し替え）:

  • 復元契約を chunks.join('') === text を厳密一致に固定する（「末尾改行差のみ許容」という曖昧条項を削除）。これを満たすには「行に '\n' 再付与」ではなく、元テキストを区切り位置で slice して連結が原文に一致する」方式に統一する（区切り文字 \n を後続 chunk 側に含めるか前 chunk 側に含めるかを1つに固定）。最も単純で検証しやすいのは「\n は直前の行の末尾に残す。最終行には付与しない」= text.split('\n') 後、index < last の行のみ + '\n'。
  • 各 chunk の実長判定は「改行付与後の文字列長」で行い ≤ limit を保証。強制スライスも同じ実長基準にする。
  • 空行（"" → 再付与で "\n"）は単独 flush せず必ずバッファに連結する、と明記。
  • テストに「ランダム/代表テキストで join('') === text を property 的に確認」を1ケース必須化し、サンプル output/newsletter-kSmyXNiKZDznRMGx4G9c.txt（末尾改行なし・\n\n 段落・URL 行）を実フィクスチャに採用する。

M2 [blocker] AC2「空入力 → 空配列」と post() の整合が未検証ライン

ADR 項1は text === '' で []、post() は空配列なら「送信0件・success 扱い」。だが Discord API は空 content の POST を 400 で拒否する。実害は「txt が空文字のテーマ」で post() が成功扱いになり、運用上は無送信が成功に化ける点。build-html/generate が空 txt を出すケース（生成失敗で空ファイル）が現実にあり得る。
提案: AC2 に「空入力 = 空配列 = POST を一切発行しない」ことを明示し、post() の DiscordPostResult で totalChunks: 0 を返す。さらに post-to-discord.ts 側で「txt が空（または空白のみ）のテーマは warn ログ + skip」を AC4 の契約に追加する（成功と誤認させない）。テストで「空文字で fetch が0回呼ばれる」を assert。

M3 [major] AC5 / workflow の条件式が既存記法と不整合・continue-on-error の効果が限定的

  • 条件式: AC5 は「has_themes==true かつ dry_run!=true」。既存 workflow の Send ステップは if: steps.fetch-themes.outputs.has_themes == 'true' && inputs.dry_run != true（has_themes は文字列 'true' 比較、step output 経由）。Discord ステップも同一の文字列比較・同一 step 参照を使うこと、を AC5/ADR に固定で書く。== true（bool）と == 'true'（str）の取り違えは GA で頻出のサイレント不発バグ。T4 への明示指示が必要。
  • continue-on-error の射程: continue-on-error: true は「後続ステップを止めない」だけで、ジョブ全体の結論は success になる（失敗が緑で隠れる）。lead 裁定「exit 非ゼロで可視化」の意図は、continue-on-error 単独では達成されない（赤くならない）。可視化したいなら GA のannotation（::error:: 出力）を post-to-discord 側で必ず吐くか、ステップに id を付けて後続の summary ステップで steps.<id>.outcome == 'failure' を拾い ::warning:: を出す設計を AC5 に足すこと。現状の AC5 文面では「非ゼロにしたのに誰も気づかない」になる。
  • 配置順: 「send-newsletter 後段・update-timestamp より前か後か」が未確定。timestamp 更新は配信成功の記録なので、Discord は send-newsletter の後・update-timestamp の前後どちらでも可だが、Discord 失敗が timestamp 更新を止めないこと（continue-on-error がそれを担保）を AC5 に明記。Mermaid 図では DSC -. continue-on-error .-> TS と update-timestamp の前提に見えるので、順序を文章でも固定する。

Nice-to-have（GO を妨げないが入れると堅牢）

N1 [major→推奨] global fetch のモック方法が ADR に未記載

観点6。既存テスト（email-sender.test.ts）は vi.mock('resend') でコンストラクタ注入をモックしている。だが DiscordSender は global fetch 直叩きなので注入点がない。ADR は「fetch はグローバル」とだけ書き、テスト手段を示していない。実装者がここで詰まるか、テストのために fetch を constructor 注入に変えて IF が揺れるリスク。
提案: ADR の Consequences/テスト節に「vi.stubGlobal('fetch', vi.fn()) でモック、afterEach で vi.unstubAllGlobals()」を明記。これで IF（constructor は token のみ）を変えずに済む。加えて429 の retry_after 待機をテストするには vi.useFakeTimers() + delay() を fake timer で進める必要があり、その手順も1行添えると T3 が迷わない（delay を email-sender 同様モジュール内 free function にしておくと fake timer で制御可）。

N2 [minor] 429 の retry_after 単位とヘッダ二重ソースの優先順位

Decision 3 は body retry_after（秒・小数）を採用し、Retry-After ヘッダも「見てよい」。だが Discord の body retry_after は秒（小数）、HTTP ヘッダ Retry-After は整数秒で、両方来た場合の優先順位が未定義。提案: 「body JSON の retry_after を一次ソース、パース失敗時のみヘッダ、両方無ければ 1s*(retry+1)」と順位を固定。また retry_after が異常に大きい値（API 異常時）に備え上限クランプ（例 60s）を入れると無人実行でのハング暴走を防げる。

N3 [minor] txt 不在 vs 空 txt の区別、JSON パース失敗時の挙動

AC4 は「txt 不在は skip + ログ」。一方 output/themes.json 自体が無い/壊れている場合の挙動が未定義（send-newsletter は throw する）。post-to-discord も同様に「themes.json 不在 → 明示エラー（exit 1）」を AC4 に1行足すと、後続で fetch-themes が exit 2（テーマ0）した場合との切り分けが明確になる。なお workflow 側で has_themes=='true' ガードがあるので実運用では到達しにくいが、手動 npm run post-to-discord 時の事故防止になる。

N4 [minor] 正規化しない判断は現データでは妥当。ただし将来リスクの監視点

観点（Decision 4）。実フィクスチャ newsletter-kSmyXNiKZDznRMGx4G9c.txt を確認: # 見出しなし・行頭 > なし・triple backtick なし・=== は setext 非対応で無害。「正規化しない」は現状 ✅ 妥当。 ただし強制スライス（M1 項4）でURL 行が分割境界をまたぐと Discord の自動リンクが切れて URL が2チャンクに割れる。サンプルの URL 行は最長でも ~120 字で limit(1900) 内に収まるため実害なしだが、「単一行強制スライスは URL を割り得る」を ADR の既知トレードオフに1行記録しておくと将来の誤解を防ぐ。連番プレフィックス非付与（lead 裁定）は尊重。

N5 [minor] ADR が ADR であるべき決定を内包している点は適切

Decision 1–5 はいずれも ADR 化されており、追加で ADR 化すべき隠れた決定は見当たらない。強いて言えば「逐次送信・並列化しない」「部分配信を許容（全停止しない）」は重要な振る舞い決定で、Alternatives に却下理由付きで記載済み。✅ 問題なし。

結論

条件付き GO。 Must-fix M1（分割規約の自己矛盾解消・復元契約の厳密化）・M2（空入力で POST 0 件 + 空 txt skip）・M3（workflow 条件式の文字列比較固定 + 失敗の annotation 可視化 + 配置順明記） を T3/T4 着手前に ADR/AC へ反映すれば実装 GO 可。M1 は inspector が AC2 を判定する根拠が崩れるため最優先。Nice-to-have N1–N4 は実装中に取り込めば足りる。
